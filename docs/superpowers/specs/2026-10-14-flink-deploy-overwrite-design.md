# Flink 部署同名 JAR 覆盖设计

## 背景与目标

当前部署脚本使用 Git 短 SHA 生成远端 JAR 文件名。相同提交在不同构建时间生成的 fat JAR 可能因归档时间戳等因素产生不同 SHA-256；远端已有同名文件时，脚本因此拒绝部署。

本次调整要求：远端目标 JAR 同名且内容不同时允许覆盖，同时继续保证传输不完整、摘要不一致或覆盖失败时不会停止旧作业或提交新作业。

## 选定方案

采用“临时上传、摘要校验、原子覆盖”：

1. 本地构建完成后计算 JAR SHA-256。
2. 远端目标文件不存在时，沿用临时上传后发布的流程。
3. 远端目标文件存在且摘要相同时，直接复用，不重复上传。
4. 远端目标文件存在且摘要不同时，先把新 JAR 上传到同目录唯一临时文件。
5. 校验临时文件 SHA-256 与本地一致后，使用同文件系统内的 `mv -f` 原子替换目标路径。
6. 替换后再次读取目标文件 SHA-256；只有与本地一致才允许进入停止旧作业和提交新作业阶段。
7. 上传、临时摘要、移动或最终摘要校验任一步失败，停止部署并报告；尽力清理本次临时文件，不触碰旧作业。

不使用 `scp` 直接写最终路径，因为传输中断可能暴露部分写入的 JAR。不改用内容摘要文件名，因为用户明确要求同名时覆盖。

## 行为边界

- 覆盖仅针对脚本根据当前干净 Git HEAD 生成的版本化目标路径。
- 不删除 checkpoint、savepoint 或其他历史 JAR。
- 覆盖发生在停止或取消旧作业之前。
- 若覆盖完成后最终摘要异常，脚本报告失败且不停止旧作业；目标文件可能已经被替换，失败报告必须明确当前阶段，供人工检查。
- 相同摘要仍复用目标文件，避免无意义上传。
- 继续要求干净工作区、构建前后 Git revision 一致、远端临时文件摘要匹配。
- 此变更不降低每次部署的两阶段人工门禁：仍须先确认部署，再单独选择是否从 savepoint 恢复。
- 部署失败后不自动重试，也不自动回滚。

## 测试策略

在现有 fake PATH 部署测试中先建立失败场景，再实现最小变更：

- 同名目标摘要不同：应上传临时文件、校验、执行 `mv -f` 覆盖、校验最终摘要，然后才继续作业操作。
- 同名目标摘要相同：仍应复用，不上传、不覆盖。
- 临时上传摘要不一致：清理临时文件，不覆盖目标，不停止旧作业。
- 原子覆盖失败：清理临时文件，不停止旧作业。
- 覆盖后目标摘要不一致或无法读取：停止，不停止旧作业或提交新作业。
- 新目标不存在：继续完成上传、安装及最终摘要校验。
- 保留部署确认、恢复模式、作业状态、savepoint 和 30 秒运行验证的现有测试。

完整验证包括 Shell 语法检查、全部部署脚本测试、Flink Maven `clean verify`、Skill 校验和 `git diff --check`。测试环境不得连接真实 Ubuntu。

## 后续真实部署

代码修改、审查、合并和推送完成不等于部署完成。由于上一轮部署已经失败，重试前必须重新执行只读预检，并再次询问用户：

1. 是否确认本次部署到 Ubuntu；
2. 新程序是否从 savepoint 恢复。
